# 在线商城 · 独立服务站 —— 设计与实现文档

> **版本**：v1.0（已实施）
> **适用项目**：在线商城 · 独立服务站（本仓库）
> **参考素材**：TechShop 截图（仅作交互与视觉参考）
> **技术底座**：PHP 7.4+ / 8.x + SQLite + AES-256-CBC 加密 JSON + 后台入口 admin.php
> **部署**：整目录上传到任意 PHP 空间，绑定域名或子目录即可运行

## 〇、结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 是否可行？ | **已落地运行**：独立部署的站点、独立订单库，可整目录迁移 |
| 数据后端选哪个？ | **SQLite**（`data/shop.db`）存订单 + **AES 加密 JSON**（`data/shop.json`）存商品/分类/收款码/推送配置 |
| 要不要装数据库服务？ | **不要**。SQLite 是 PHP 内置扩展（`pdo_sqlite`），零安装、单文件、可随站点一起备份 |
| 消息推送用什么？ | **自建 ntfy 为主通道**（安卓 App 体验最好） + **通用 Webhook 兜底通道**（同一套模板覆盖 Bark / PushMe / Gotify / 企业微信 / 钉钉 / 飞书），另支持邮件 SMTP |
| 前端怎么做？ | 根目录 `index.php` 商品墙 + 下单/收款弹窗；`query.php` 查询；`api.php` AJAX |
| 后台怎么加？ | `admin.php` 用 `?sub=` 切换子页（orders / products / categories / page / pay / push / security / log） |
| 收款码怎么放？ | 不做图片上传，收款码做成**图片 URL 配置项**，支持聚合码或微信/支付宝分开 |
| 核心闭环工期 | P0 约 **2 个工作日**（商品展示→下单→收款→我已付款→后台确认→推送） |

## 二、项目现状

| 项 | 现状 | 对本方案的影响 |
|---|---|---|
| 运行环境 | 原生 PHP（7.4+ / 8.x），无需框架与 Composer；SQLite 为 PHP 内置扩展 | 整目录上传即可运行，无需额外环境 |
| 数据存储 | `data/shop.json`（AES-256-CBC 加密配置）+ `data/shop.db`（SQLite 订单库） | 配置与订单分离，备份时整个 `data/` 一起打包 |
| 后台 | `admin.php` 入口 + `inc/admin_view.php` 渲染，`?sub=` 切换子页 | 商城后台即独立后台，不挂载到任何外部模块体系 |
| 前台 | 站点根目录 `index.php` 商品墙、`query.php` 订单查询、`api.php` AJAX 出口 | 无需子目录，访问站点根路径即可 |
| 图片 | 全部使用外链 URL，不提供上传 | 收款码与商品图均做 URL 配置项，避免新增上传安全面 |
| 安全 | `secret/config.secret.php` 存 AES 密钥；部署时将 `data/`、`secret/` 设为不可直接访问 | `data/shop.db` 与配置天然不暴露 |
| 超时/异步 | 使用 `register_shutdown_function` / `fastcgi_finish_request` 做响应后推送 | 推送不拖慢客户下单响应 |

## 三、数据后端选型

### 3.1 候选对比

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **A. 沿用 AES 加密 JSON（单文件）** | 零新概念；与现有完全一致 | 读-改-写非原子，并发下单会**丢单**；订单上千后每次全量读写变慢；无索引/分页 | 订单量极小的玩具场景 |
| **B. 一订单一 JSON 文件**（`data/orders/{订单号}.json`） | 零扩展依赖；`fopen(...,'x')` 天然防重复、无锁竞争；单条读写快 | 列表需 `glob` 全扫；统计/筛选要做内存聚合；文件数多了慢 | 无 SQLite 扩展时的**兜底方案** |
| **C. SQLite（PDO）** ✅ | PHP 内置；单文件随站备份；事务/唯一索引/分页/聚合全支持；WAL 模式读并发好；`data/` 可配置为禁止直接访问 | 需要 `pdo_sqlite` 扩展（PHP 8 默认自带）；后台需要多写一点 SQL | **推荐** |

### 3.2 推荐：C（SQLite）为订单主库 + A（加密 JSON）为配置库

**分工理由**：
- **订单**是「高频写 + 需要事务 + 需要唯一订单号 + 需要按状态筛选/分页/统计/导出」的数据 —— 这正是关系库的强项，JSON 的弱项。
- **商品 / 分类 / 收款码 / 推送配置**是「低频写 + 全量读 + 后台整体保存」的数据 —— 与现有 AES 加密 JSON 配置的读写方式完全同构，沿用 `loadEncryptedData`/`saveEncryptedData` 最省事，还能自动享受 AES 加密。

**数据库落地细节**：
```php
// inc/shop_store.php 内
$db = new PDO('sqlite:' . __DIR__ . '/../data/shop.db');
$db->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
$db->exec('PRAGMA journal_mode = WAL');     // 读写并发更好
$db->exec('PRAGMA busy_timeout = 5000');    // 写锁等待 5 秒，避免 SQLITE_BUSY
$db->exec('PRAGMA foreign_keys = ON');
```
> **上线前自检一行**：`<?php var_dump(extension_loaded('pdo_sqlite'));` —— 若为 `false`（极少数精简主机），直接切兜底方案 B，仓储层接口不变，业务代码零改动。

### 3.3 兜底方案（无 pdo_sqlite 时）
`inc/shop_store.php` 里做**仓储层抽象**，对外只暴露 `OrderStore` 接口：
`create() / get($orderNo) / markPaid() / markVerified() / list($filter,$page) / stats()`
- 实现一：`SqliteOrderStore`
- 实现二：`JsonFileOrderStore`（一订单一文件 + `flock` + `glob` 聚合）
切换只改一行配置，前端与后台代码**完全不动**。

### 4.2 `data/shop.db`（SQLite，订单与推送）

```sql
-- 订单主表
CREATE TABLE IF NOT EXISTS orders (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  order_no      TEXT    NOT NULL UNIQUE,        -- ORD20260930194043BMXY
  pay_code      TEXT    NOT NULL,               -- 付款备注码：EK
  mode          TEXT    NOT NULL DEFAULT 'now', -- now=立即服务 / booking=预约
  status        TEXT    NOT NULL DEFAULT 'pending_payment',
  customer_name TEXT    NOT NULL,
  wechat        TEXT    NOT NULL,
  phone         TEXT    NOT NULL,
  book_date     TEXT    NOT NULL DEFAULT '',    -- 2026-10-01
  book_slot     TEXT    NOT NULL DEFAULT '',    -- 上午 / 下午 / 晚上 / 随时
  remark        TEXT    NOT NULL DEFAULT '',
  items_json    TEXT    NOT NULL,               -- [{"id","name","price","qty","unit","cat"}]
  amount        REAL    NOT NULL DEFAULT 0,
  client_ip     TEXT    NOT NULL DEFAULT '',
  ua            TEXT    NOT NULL DEFAULT '',
  pay_marked_at TEXT    NOT NULL DEFAULT '',    -- 客户点「我已付款」的时间
  verified_at   TEXT    NOT NULL DEFAULT '',    -- 后台点「确认已付款」的时间
  verified_by   TEXT    NOT NULL DEFAULT '',    -- 操作管理员账号
  admin_note    TEXT    NOT NULL DEFAULT '',
  created_at    TEXT    NOT NULL,
  updated_at    TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_orders_status  ON orders(status);
CREATE INDEX IF NOT EXISTS idx_orders_created ON orders(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_orders_wechat  ON orders(wechat);
CREATE INDEX IF NOT EXISTS idx_orders_phone   ON orders(phone);
CREATE INDEX IF NOT EXISTS idx_orders_code    ON orders(pay_code);

-- 推送队列（失败重试用）
CREATE TABLE IF NOT EXISTS push_queue (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  order_no   TEXT    NOT NULL,
  event      TEXT    NOT NULL,                  -- created / paid / test
  channel    TEXT    NOT NULL,                  -- ntfy / webhook
  payload    TEXT    NOT NULL,
  attempts   INTEGER NOT NULL DEFAULT 0,
  next_try   INTEGER NOT NULL DEFAULT 0,        -- unix 时间戳
  status     TEXT    NOT NULL DEFAULT 'pending',-- pending / sent / failed
  last_error TEXT    NOT NULL DEFAULT '',
  created_at TEXT    NOT NULL,
  sent_at    TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_pq ON push_queue(status, next_try);

-- 推送日志（后台可看，排查用）
CREATE TABLE IF NOT EXISTS push_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  order_no   TEXT NOT NULL DEFAULT '',
  channel    TEXT NOT NULL DEFAULT '',
  http_code  INTEGER NOT NULL DEFAULT 0,
  response   TEXT NOT NULL DEFAULT '',
  success    INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
```

**订单号规则**（与截图 `ORD20260930194043BMXY` 完全一致）
```
'ORD' . date('YmdHis') . 4位随机大写字母数字
= 3 + 14 + 4 = 21 字符
```
用 `UNIQUE` 索引兜底，冲突则重试生成（最多 5 次）。

## 五、订单状态机

```
                    ┌──────────────────────────────┐
                    │  pending_payment  待付款      │  客户已下单（建单瞬间）
                    │  （= 客户已下单）             │
                    └───────────────┬──────────────┘
        客户点「我已付款」           │            后台「取消订单」/ 超时
                                    ▼                     ▼
                    ┌──────────────────────────────┐   ┌──────────────┐
                    │  awaiting_verify  待核查      │   │  cancelled   │
                    │  （付款进度待人工核查）        │   │   已取消      │
                    └───────┬──────────────┬───────┘   └──────────────┘
       后台「确认已付款」     │              │  后台「付款失败」
                            ▼              ▼
                ┌──────────────────┐  ┌──────────────────┐
                │  paid  已付款     │  │ payment_failed   │
                │（下单流程完成）    │  │    付款失败       │
                └────────┬─────────┘  └──────────────────┘
       后台「开始处理」   │
                         ▼
                ┌──────────────────┐   后台「标记完成」
                │ processing 处理中 │ ──────────────────────▶ completed 已完成
                └──────────────────┘
                         │
       任意活跃状态 ──▶ refunding 退款中 ──▶ refunded 已退款
```

**你要求的最小闭环（P0 必须实现）**：
`pending_payment`（客户已下单）→ 客户点「我已付款」→ `awaiting_verify`（待人工核查）→ 后台点「确认已付款」→ `paid`（下单流程结束）✅

**状态 → 中文标签映射**（后台筛选标签用）

| status | 中文 | 颜色 |
|---|---|---|
| `pending_payment` | 待付款 | 灰 |
| `awaiting_verify` | 已确认待处理 / 付款待核查 | 青（截图为青色 `#22d3ee`） |
| `paid` | 已付款 | 绿 |
| `payment_failed` | 付款失败 | 红 |
| `processing` | 处理中 | 紫 |
| `completed` | 已完成 | 深绿 |
| `cancelled` | 已取消 | 灰 |
| `refunding` / `refunded` | 退款中 / 已退款 | 橙 |

## 六、前端设计

### 6.1 目录与页面结构

```
站点根目录/
├── index.php      # 商品展示墙 + 下单弹窗 + 收款弹窗（单页搞定）
├── api.php        # 唯一 AJAX 出口：action=create / mark_paid / query / regen_code
└── query.php      # 订单查询独立页
```

**为什么用单页 + 弹窗**：截图里的交互就是「列表 → 确认订单弹窗 → 收款弹窗」，单页体验最顺；且避免多页面间的状态传递。

| 合计 | 只读 | — | — | 大字高亮 |
| [提交订单] | 主按钮 | — | — | |

**前端校验**：手机号 `/^1[3-9]\d{9}$/`、微信号长度 2-30、称呼长度 1-20，实时红字提示。

### 6.4 收款页（关键设计 —— 备注码机制）

```
┌──────────────────────────────┐
│         [收款码大图]           │
│           PIN(**)            │
├──────────────────────────────┤
│ 💳 付款备注码（转账时请在备注/  │
│    附言中填写，方便对账）       │
│                              │
│           E K        [换一个] │  ← 超大字号 + 复制按钮
│        （或 您的微信：wxid_xx）│
├──────────────────────────────┤
│ 订单号     ORD20260930194043BMXY │
│ 联系人     张三               │
│ 联系方式    1234567890        │
│ Steam 代安装 × 1      ￥15    │
├──────────────────────────────┤
│ 应付                 ￥15     │
├──────────────────────────────┤
│ 扫码支付完成后请联系管理员确认；│
│ 付款时请务必填写上方备注码      │

│ [💬 联系管理员]               │
└──────────────────────────────┘
```

**为什么需要「备注码」**：微信/支付宝**个人收款码没有任何支付回调**，你只能靠收款账单里的「备注」来认人。所以备注码是对账的唯一锚点。

**两种模式（后台可切）**：
- `short`（推荐，截图方案）：系统生成 2-4 位短码（如 `EK`），**保证短、好输、当日尽量不重复**；页面上同时用大字显示「您的微信」，提示语写成「备注请填 **EK**（或直接填您的微信）」。后台订单列表有独立的「备注码」列，收款时一眼匹配。
- `wechat`：备注码就是客户微信本身，最直观、零歧义，缺点是长微信号输入麻烦。

**「换一个」按钮**：调 `api.php?action=regen_code&order_no=xxx`，校验订单归属后重掷短码（仅 `pending_payment` 状态可换）。

### 6.5 「我已付款」按钮

点击 → 二次确认弹窗「请确认您已完成付款，管理员核对后将为您安排服务」→ `POST api.php action=mark_paid`（带订单号 + 手机号后 4 位校验）→ 状态转 `awaiting_verify` → 前端切换为绿色成功态「已提交付款信息，等待管理员核实」→ **同时触发 `paid` 事件推送**。

### 6.6 订单查询页 `query.php`

- 输入：**订单号 + 手机号后 4 位**（或微信）双因子，防遍历
- 输出：订单号、商品、金额、状态（中文 + 颜色）、预约时间、下单时间、备注
- 不显示：其他客户的任何信息；不提供订单列表接口
- 限频：同 IP 10 次/10 分钟，失败也计数
- 文案呼应你的需求：「填写电话与微信是为了让您在此自助查询订单」

## 八、消息推送设计

### 8.1 方案对比（你要的：开源 / 可自建 / 有安卓 App）

| 方案 | 可自建 | 安卓 App | 协议 | 评价 |
|---|---|---|---|---|
| **ntfy** ✅ | ✅ Docker 一键 | ✅ **官方 App**（Play / F-Droid） | HTTP `POST /topic`，极简，支持 JSON、附件、优先级、标签、动作按钮 | **首选**：自建 + 安卓体验最好 + 无需账号体系 |
| **Gotify** | ✅ Docker | ✅ 官方 App | REST + token | 备选，同样优秀，但消息格式比 ntfy 啰嗦些 |
| Bark | ⚠️ 服务端开源 | ❌ 主打 iOS | HTTP GET | 你有安卓机，不选 |
| PushMe Server | ✅ | ✅ | HTTP | 生态小、维护弱，不选 |
| Hotify | 半开源 | 一般 | HTTP | 资料少，不选 |
| 企业微信 / 钉钉 / 飞书 机器人 | ❌ 依赖平台 | ✅（装对应 App） | Webhook | **零部署零成本，国内最稳，作为兜底通道** |
| Server酱 / WxPusher | ❌ | 微信接收 | HTTP | 不用装 App，但有配额与第三方依赖 |

### 8.2 推荐组合：双通道 + 通用模板

```
通道 1：自建 ntfy         → 主通道，安卓 App 秒收，可点通知直接跳后台
通道 2：通用 Webhook      → 兜底通道，一个通道覆盖 Bark / PushMe / Gotify / 企业微信 / 钉钉 / 飞书
```

**「通用 Webhook」是本方案的关键抽象**：后台只暴露 `URL + Method + Headers + Body 模板` 四个输入，`{text}` / `{title}` 为占位符。于是：

| 平台 | URL | Body 模板 |
|---|---|---|
| 企业微信 | `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx` | `{"msgtype":"text","text":{"content":"{text}"}}` |
| 钉钉 | `https://oapi.dingtalk.com/robot/send?access_token=xxx` | `{"msgtype":"text","text":{"content":"{text}"}}` |
| 飞书 | `https://open.feishu.cn/open-apis/bot/v2/hook/xxx` | `{"msg_type":"text","content":{"text":"{text}"}}` |
| Bark | `https://api.day.app/你的KEY/{title}/{text}?group=订单` | *(GET，留空)* |
| Gotify | `https://gotify.你的域名/message?token=xxx` | `{"title":"{title}","message":"{text}","priority":5}` |
| PushMe | `https://push.i-i.me/?push_type=post&push_key=xxx` | `{"title":"{title}","content":"{text}","date":"","type":"text"}` |

> 一次开发，覆盖你列出的**全部**候选方案 —— 这是最省事且不锁死的技术选择。

### 8.3 推送架构（必须异步，不能拖慢下单）

```
客户点「提交订单」
   │
   ├─ api.php action=create
   │    1. 校验字段 / 限频 / honeypot
   │    2. 生成订单号 + 备注码
   │    3. INSERT INTO orders（事务）
   │    4. 返回 JSON：订单号 + 收款页数据      ← 客户这里就拿到响应了
   │
   └─ register_shutdown_function(...)   ← 响应已发给客户后才执行
         └─ inc/push.php::dispatch('created', $order)
              1. 渲染模板 → 得到 {text}
              2. INSERT INTO push_queue（每个启用的通道一行）
              3. 逐通道发送：curl，超时 3 秒，连接超时 2 秒
                   ├─ 2xx → push_log(success=1)，queue.status=sent
                   └─ 其他 → attempts+1，next_try = now + 退避，status=pending
```

**更强的做法（可选）**：`api.php` 里先 `fastcgi_finish_request()`（OpenResty/FPM 下有效）再推送，比 `register_shutdown_function` 更彻底。代码里两者都用，并做函数存在性判断。

### 8.4 自建 ntfy（Docker 示例）

```bash
# 在可运行 Docker 的服务器上执行
docker run -d --name ntfy \
  -p 8080:80 \
  -v /opt/ntfy:/var/cache/ntfy \
  binwiederhier/ntfy serve --cache-file /var/cache/ntfy/cache.db
```
1. 新建反向代理站点 `ntfy.你的域名` → `127.0.0.1:8080`，申请 Let's Encrypt 证书
2. 手机装 **ntfy** App（应用商店 / F-Droid）→ `Settings → Manage users → 添加自建服务器 https://ntfy.你的域名`
3. 在 App 里订阅 topic（如 `xiaowei-order`）
4. 后台「推送设置」里填：服务器 `https://ntfy.你的域名`、topic `xiaowei-order`
5. 点「测试推送」→ 手机应立刻收到

**发送示例**
```http
POST https://ntfy.你的域名/xiaowei-order
Content-Type: text/plain

🛒 新订单 ORD20260930194043BMXY
```
或 JSON 模式（可加标题/优先级/标签/点击跳转）：
```json
{
  "topic": "xiaowei-order",
  "title": "新订单通知",
  "message": "🛒 新订单 ORD2026...\n商品：Steam 代安装×1\n金额：￥15",
  "priority": 4,
  "tags": ["shopping_cart"],
  "click": "https://你的域名/admin.php?sub=orders"
}
```
**鉴权（强烈建议）**：ntfy 开启 `--auth-file` 后，请求头带 `Authorization: Bearer tk_xxxxxxxx`。

### 8.6 重试与降级

- **退避策略**：30s → 2min → 10min → 1h → 6h，最多 8 次，之后 `status=failed`（后台显示红点，可「手动重发」）
- **有 cron**（服务器计划任务）：
  ```
  */2 * * * * /usr/bin/php /path/to/site/cron/push_retry.php
  ```
- **无 cron（共享主机）**：**懒重试** —— 后台每次打开「订单管理」或「推送设置」页时，顺手处理最多 5 条到期队列项；客户访问前台任意页面也触发一次（`ignore_user_abort(1)` + 总耗时上限 5 秒）。
- **通道降级**：任一通道失败不影响其他通道；两通道全失败也不影响订单落库（订单先入库，推送只是通知）。

## 九、安全设计

| 风险 | 对策 |
|---|---|
| 刷单 / 垃圾订单 | 使用内置限流：单 IP **5 单 / 10 分钟**；同 IP 两次提交间隔 < 3 秒判为机器人；表单加隐藏 honeypot 字段 |
| 订单号被遍历查询 | 订单号含 `YmdHis` + 4 位随机（约 1.6M 组合/秒），再加**手机后 4 位双因子**校验；查询接口独立限频（10 次/10 分钟） |
| 「我已付款」被恶意触发 | 必须带订单号 + 手机后 4 位匹配；仅 `pending_payment` 状态可转 |
| 后台接口 CSRF | 新增表单全部用 `csrf_field()`；AJAX 校验 `$_SESSION['csrf_token']` |
| XSS | 所有客户输入（称呼/微信/电话/备注）输出一律 `htmlspecialchars`；AJAX 用 `textContent` 而非 `innerHTML` |
| SQL 注入 | 全量 PDO 预处理语句，禁止字符串拼接 |
| 个人信息泄露 | `data/` 已配置为禁止直接访问；可选对 `wechat` / `phone` 做 AES 字段级加密（复用 `AES_KEY`），DB 文件被拖也不直接明文 |
| 数据库文件被下载 | 已在 `data/` 下 → 部署规则自动拦截；上线后验证 `/data/shop.db` 返回 403 |
| 收款码被替换 | 收款码只存 URL，改它需要登录后台（后台账号体系） |
| 库存超卖 | 下单时 `UPDATE ... SET stock = stock - qty WHERE id = ? AND (stock = -1 OR stock >= qty)`，受影响行数 0 则回滚 |
| 推送 URL 泄露 | 推送配置存在 AES 加密的 `shop.json`，后台页面回显时对 token/key 做掩码 |
| 隐私合规 | 表单底部固定展示用途说明（你已明确要求），文案后台可改 |

## 十二、风险与注意事项

1. **个人收款码无支付回调** —— 这是整个方案的物理限制。「我已付款」永远是**客户自述**，必须人工核查。因此：
   - 备注码要做**非常大、非常显眼、一键复制**；
   - 后台列表必须把备注码/微信放在一眼能看到的位置；
   - 后台首页建议加一个「待核查 N 单」的红色提醒。
2. **备注码重复风险** —— 微信收款账单只显示备注文本。若两位客户都用了 `EK`，只能靠金额 + 时间二次区分。缓解：短码长度可配（推荐 2 位但**当日不重复**），并在后台按 `pay_code` 建索引便于检索。
3. **推送被墙 / 自建服务器掉线** —— 双通道（自建 ntfy + 企业微信机器人）几乎可以兜住；再不行还有后台「待核查」角标兜底。
4. **无 cron 的主机** —— 已设计懒重试，推送延迟最多到下一次后台访问，可接受。
5. **SQLite 写锁** —— 必须开 WAL + `busy_timeout=5000`，否则并发下单偶发 `database is locked`。
6. **后台文件体积** —— 渲染块已抽到 `inc/admin_view.php`，`admin.php` 保留入口、路由与写操作处理，避免单文件继续膨胀。
7. **不要上传 `.md` 文档到服务器** —— 本文档只在本地保留，生产环境只上传运行所需文件。

### 15.4 IP 归属地识别

新增 `inc/ip_geo.php`，**在线优先、离线兜底**，IPv4/IPv6 都支持：

```
内网/保留地址 → 本地判定，不查外部
本地缓存     → data/ip_geo_cache.json（AES 加密，30 天）
在线多源     → ipchk.cn（多库聚合）→ ip2location → ip-api → ip.sb → ipinfo → ipwho.is → pconline
离线兜底     → data/ip2region.xdb / ip2region.v6.xdb
```

**为什么是服务端查**：免费接口多半只有 HTTP，前端查会被混合内容策略拦；前端查还会把客户 IP 直接暴露给第三方；服务端才能缓存 + 多源重试。

**多库投票**：用 11 个位置公开的国内公共 DNS 做基准实测，`geocn`/`ip2region`/`qqwry` 各 88%、ip-api 82%，但**错的 IP 不一样**（114DNS 只有 ip-api 判错成山东济南）。所以改为**先投票选省份、再在省份一致的库里投票选城市**，基准 16/16 = 100%。区县取自 `geocn.district`（数据源有就给）。

**踩过的三个坑**（都已修）：
1. `ip_geo_join()` 按位置取前 3 项拼串，城市为空时 ISP 会**上移占位**，输出成「中国 上海市 电信」
2. 省市**跨源混搭**会产生「陕西 北京市」这种自相矛盾，改为投票 + 省市同源
3. `country` 字段来自 qqwry 是**繁体**「中華人民共和國」，加了归一化映射

**必需扩展**：只依赖 PHP 核心函数。曾经用了 `bccomp()`（BCMath）和 `iconv()` 却没做兼容判断 —— **部分主机的 PHP 默认不带 bcmath**，缺失时致命错误导致接口返回非 JSON，前端只显示「接口未返回数据」。已改为 `inet_pton` + `strcmp` 做区间比较，`iconv` 加 `function_exists` 判断。

**模块守卫**：`inc/ip_geo.php` 原写成 `if (!defined('SHOP_GEO_OK')) { die('Access denied'); }`（抄了 `crypt.php` 的硬守卫）却没配套 define，任何入口 require 它都会直接输出 13 字节的 `Access denied`。已改为与 `shop_store.php`/`push.php` 一致的**自我定义**写法。

## 十六、软删除与操作审计（2026-10-02 补）

### 16.1 为什么把「自动删除」改成「软删除」

第十五节的 15.2 实现的是**硬删除**：超时未付款的订单直接从库里删掉。

但用户随后提出：**「我需要在订单管理中看到已提交但未付款的订单」** —— 硬删除会让这些记录彻底消失，看不到「谁下了单没付款」。

两个需求并不矛盾，用**软删除 + 延迟硬删**同时满足：

| 阶段 | 状态 | 在列表里 | 计入统计 | 占未付款名额 | 记录 |
|---|---|---|---|---|---|
| 提交未付款 | `pending_payment` | 显示 | 是 | 是 | 保留 |
| 超时（默认 10 分钟） | **`expired` 已失效** | 默认不显示，切「已失效」标签页可见 | **否** | **否** | 保留 |
| 超过保留期（默认 7 天） | —— | 不显示 | 否 | 否 | **彻底删除** |

**实现要点**：
- `shop_order_expire_unpaid()` 从 `DELETE` 改为 `UPDATE ... SET status='expired'`
- 新增状态 `expired`；`shop_order_stats()` 累加 `total` 时排除它
- `shop_order_list()` 在 `status` 为 `all`/空时追加 `status <> 'expired'`，选 `expired` 标签才返回
- 新增 `shop_order_purge_expired($days)` 做最终硬删，由 `shop_order_expire_unpaid()` 按配置顺带调用
- 新增配置 `pay.expired_keep_days`（默认 7，`0` = 永久保留）

**安全边界不变**：只处理 `pending_payment` / `payment_failed` 且 `pay_marked_at` 为空的订单；客户点过「我已付款」（`awaiting_verify`）的**永远不会被标记失效**。

### 16.2 操作审计日志

审计日志统一由 `inc/shop_store.php` 中的同一套表结构与函数实现：

```sql
CREATE TABLE audit_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at TEXT, ip TEXT, ua TEXT, user TEXT,
  action TEXT, target TEXT, detail TEXT, result TEXT
);
```

**核心设计：中央钩子 + shutdown 回填**

写操作处理器都是「处理完就 `header + exit`」，在钩子里拿不到最终成败。所以：

1. 在写操作真正执行**之前**，按 `$_POST['action']` / 一组已知 `$_GET` 键识别出动作，先 `shop_audit_add()` 记一笔，拿到 id
2. `register_shutdown_function` 在脚本收尾时读 `$_SESSION['save_msg']`，用它 `shop_audit_set_result()` 回填 `result`

关键细节：记日志前先 `unset($_SESSION['save_msg'])`，否则会把**上一次**操作的残留消息当成这次的结果。

**动作 →中文名映射**在 `shop_audit_actions()`，新增写操作处理器时要同步登记，否则日志里只显示英文键名。

**注意**：`inc/shop_store.php` 是订单与风控的唯一数据层入口，后续改动优先在此扩展，避免在多个入口重复实现。

### 16.3 子页命名冲突的处理

站内已有 `?sub=audit` 入口。商城「操作日志」子页改用 `?sub=log`，避免串页。

**处理**：`?sub=audit` 统一**重定向到 `?sub=log`**（两者看的是同一张 `audit_log` 表，保留两套 UI 只会让人困惑）。

⚠️ 改子页名时**必须同时改三处**，少一处就会串页或 404：
1. `admin.php` 的白名单数组
2. `inc/admin_view.php` 里的 `$shopSub === 'xxx'` 渲染条件
3. 页面内部生成链接用的 `'sub' => 'xxx'`

本次就是漏了第 2 处（只改了链接没改条件），导致两个页面**互换**。

### 16.4 ⚠️ 时区不一致（重要，曾导致线上故障）

`admin.php` 第 3 行有 `date_default_timezone_set('Asia/Shanghai')`，但**前台根目录页面从来没设过** ——
它们用 php.ini 的 date.timezone = UTC。

后果：**订单 created_at 按 UTC 写入，后台「超时未付款」判定按上海时间算，两者差 8 小时**。
后台算出的「10 分钟前」比前台刚写入的下单时间晚了 8 小时 →
**未付款订单在下单的瞬间就被判定超时**，管理员在订单列表里根本看不到它们。

现象：「未付款订单查不到详细信息」。

**修复**：在 `index.php`、`query.php`、`api.php`
开头统一加 `date_default_timezone_set('Asia/Shanghai');`。

**教训**：任何「拿当前时间和数据库里的时间字符串比大小」的逻辑，
都必须先确认**写入方和读取方在同一个时区**。跨入口（前台 API / 后台）比较时尤其危险。

**遗留**：本次修复之前写入的订单 created_at 仍是 UTC 字符串，与之后写入的相差 8 小时。
历史订单的时间显示会偏 8 小时，但只影响显示，不影响业务。

### 17.6 IP 归属地：不再拼出自相矛盾的结果

**现象**：某个联通 IPv6 显示「中国 **北京市唐河县**」——唐河县属河南南阳。

**根因**：各库对该 IP 的城市本身就打架（`ipchk` 说北京、`ip2location` 说南阳、`ipinfo` 说郑州），
而 `ipchk` 自己的 `geocn` 子库也会 `city=北京市` 配 `district=唐河县`。
城市是**投票选出来的**，区县却**无条件**取 `geocn` 的，于是拼出了矛盾的组合。

**方案**：只有在「省份投票有**明确胜出者**」（票数 ≥2 且严格大于第二名）时才带区县。
票数打平说明位置本身不确定，宁可只显示城市。

1. **换标题 ≠ 换顺序**：分类管理最初我把两段 `<h3>` 的文字对调，结果标题和内容对不上，

## 十八、订单页新订单提醒（横幅 + 浏览器桌面通知）（2026-10-02 补）

### 18.1 需求

后台订单管理页要能**自己发现新订单**：右上角弹横幅，并且通过浏览器把通知推送到电脑系统。

### 18.2 实现

**后端**（`inc/shop_store.php`）新增两个函数：

- `shop_order_max_id()` —— 当前订单表最大 `id`，作为页面加载时的**基线**（避免把历史订单全播一遍）
- `shop_order_new_since($sinceId, $limit)` —— 拉取 `id > $sinceId` 的订单，按 `id ASC`，
  返回 `['latest' => 最新id, 'orders' => [...]]`。
  已失效（`expired`）的**不放进通知列表**，但 `latest` 仍然推进（跳过它，不重复扫描）

**AJAX 接口**：`?shop_ajax=new_orders&since=N`，
与 `ipgeo` 同级、**在鉴权门之后**，必须登录后台才能调；返回 JSON，`Cache-Control: no-store`。

**前端**（`inc/admin_view.php` 的订单分支）：

- 页面输出 `SHOP_LAST_ORDER_ID`（来自 `shop_order_max_id()`）与 `SHOP_NEW_ORDER_URL`
- 用 `localStorage` 记住已见过的最大 id，**刷新页面不会重复通知**
- **每 20 秒**轮询一次；`document.hidden` 时跳过，切回页面时（`visibilitychange`）立刻补查一次
- 有新订单 → 右上角绿色横幅（复用 `#admin-toast-wrap` 的 `.admin-toast`）+ `new Notification()`
- 通知内容：标题「🛒 新订单 ￥金额」，正文「客户 · 商品 / 状态 · 支付方式 / 微信」
- `tag` 设为订单号，同一单不会重复弹

### 18.3 授权按钮

订单管理搜索栏旁边新增 **🔔 开启桌面通知** 按钮，三种状态：

| `Notification.permission` | 按钮显示 |
|---|---|
| `default` | 🔔 开启桌面通知（点了会请求授权，授权成功后**立刻发一条测试通知**） |
| `granted` | 🔔 桌面通知已开启（绿色高亮） |
| `denied` | 🔕 桌面通知被拒绝（提示去地址栏左侧改「通知」为允许） |

浏览器不支持 `Notification`（或**不是安全上下文**）时，按钮**仍然显示**，只是文案变成
「🔔 桌面通知不可用 / 🔔 需要 HTTPS」，鼠标悬停能看到具体原因 —— 横幅提醒不受影响。

> ⚠️ **浏览器只在 `https://`（或 `localhost`）提供 Notification API**。
> 用 `http://` 或 `http://IP` 打开后台时 `window.Notification` 是 `undefined`，
> 桌面通知必然不可用。**第一版实现里按钮在这种情况下被直接 `display:none` 隐藏了，
> 导致用户以为功能没上 —— 已改为永远显示并说明原因。**

### 18.4 和「消息推送」的区别

| | 消息推送 | 桌面通知 |
|---|---|---|
| 谁发的 | 服务端（Gotify / ntfy / 邮件 / Webhook） | 浏览器 Notification API |
| 页面关着能收吗 | ✅ 能 | ❌ 不能，页面开着才有效 |
| 要配置吗 | 要 | 不用，点一下授权 |
| 手机能收吗 | ✅ 能 | ❌ 只在电脑浏览器里 |

两者互补：**推送保底，桌面通知让你在电脑前时第一时间看到**。建议都开。

### 18.5 踩坑

1. **基线不能是「当前页第一条」** —— 订单列表分页，第 2 页的第一条不是最新单，必须单独查 `MAX(id)`。
2. **失效单要跳过但 id 要推进** —— 否则要么刷屏通知，要么每轮都重新扫到它。
3. **轮询要判 `document.hidden`** —— 后台标签页里 20 秒一次纯属浪费，切回来补一次即可。

### 18.6 ⚠️ 第二轮修正：定时轮询改成长轮询（2026-10-02）

**用户反馈**：「浏览器最小化之后就不显示了，再次打开标签页才开始提示，这个通知还不是实时的。」

**原因（第一版的两个设计错误）**：

```js
window.shopCheckNewOrders = function(){
  if (document.hidden) return;        // ① 最小化时直接跳过 —— 而那正是最需要提醒的时候
  ...
};
setInterval(window.shopCheckNewOrders, 20000);   // ② 后台标签页定时器会被浏览器限流到 ~1 分钟
```

1. **`if (document.hidden) return;`** —— 当时想「省资源」，结果浏览器一最小化就**完全不检查**，
   等你切回来 `visibilitychange` 补查一次才弹 —— 就是你看到的现象。
2. **`setInterval`** —— 浏览器对后台标签页的定时器有节流（Chrome/Edge 通常降到 1 分钟一次），
   就算不跳过也做不到实时。

**改法：长轮询（long polling）**

- 服务端新增 `?shop_ajax=new_orders_wait&since=N&wait=50`：先查一次，没有就 `usleep(700000)` 循环等，
  **一有新订单立刻返回**，最多等 50 秒（低于 nginx `fastcgi_read_timeout` 默认 60 秒，避免被网关切断）。
- 前端**不再用 `setInterval`**：一个请求返回后**立刻发下一个**，形成连续的长轮询。
- **网络 I/O 回调不受后台节流影响** —— 所以浏览器最小化、切到别的标签，照样能秒级收到通知。

**服务端关键点**：

| 点 | 为什么 |
|---|---|
| `session_write_close()` 必须在等待前调用 | 否则长轮询会**占住会话锁**，同一个后台的其他请求（换页、保存）全部卡死 |
| `set_time_limit($wait + 20)` | 默认 30 秒执行时限会在等待中被切断 |
| `connection_aborted()` | 客户端关标签页后及时退出，不白占 PHP-FPM 进程 |
| `wait` 上限 50 秒 | 低于 nginx 默认 `fastcgi_read_timeout` 60 秒 |

**实测**（`wait=40`，第 2 秒插入订单）：**插单后 0.12 秒返回**，总耗时 2.13 秒 —— 证明是「一有就返回」而不是等满。

**前端防重复**：`shopCheckNewOrders()` 用 `__polling` 标志守卫，重复调用不会起第二条轮询链（否则会重复弹通知）。

### 18.7 第三轮修正：状态变化也提醒（客户标记已付款）（2026-10-02）

**用户反馈**：「只提醒已提交的订单（待付款状态），已付款时为何没有推送消息？」

**原因**：第一/二版的桌面通知只监控「订单表出现**新行**」（`id > since`）。
客户点「我已付款」只是把**同一行**的状态从 `pending_payment` 改成 `awaiting_verify` ——
行还是那一行，`id` 没变，所以**不触发任何提醒**。

> 而服务端推送的 `paid` 事件是「**客户已标记付款**」（`api.php` 里的 `mark_paid`），
> 默认开启；管理员自己在后台点「确认已付款」不会推送（自己操作自己，没必要）。

**改法**：新增 `shop_order_watch($sinceId, $sinceTime, $limit)`，同时盯两类事件 ——

| 事件 | 判定 | 前端文案 |
|---|---|---|
| `new` | `id > sinceId` | 🛒 新订单 ￥40 · 客户 · 商品 |
| `awaiting_verify` | `id <= sinceId AND updated_at > sinceTime AND status = 'awaiting_verify'` | 💰 **客户已标记付款** ￥40 · 客户 · 请核对到账 |

**关键点**：

1. **水位有两根**：`since`（最大 id）和 `sinceTime`（最大 `updated_at`）。两个都要持久化到 `localStorage`。
2. **用 `id <= sinceId` 排除新订单** —— 新订单的 `updated_at` 也大于水位，不排除就会**提醒两次**。
3. **只关心客户发起的动作**（`awaiting_verify`）—— 管理员自己在后台改状态不提醒。
4. 客户端新增 `shop_order_max_updated_at()` 取初始水位（不能用 `date('now')`，各库时区/秒级误差会导致漏报）。

**实测**：造单 → `event=new` ✓；改成 `awaiting_verify` → `event=awaiting_verify` ✓；再查不重复 ✓；
长轮询中把状态改成 `awaiting_verify` → **0.61 秒返回** ✓

### 18.8 第四轮修正：列表要跟着一起更新（2026-10-02）

**用户反馈**：「出现新订单了后台也不自动显示，还需要刷新一下订单列表才展示出来。
为何通知送达了，订单列表却没有同步更新？」

**原因**：前几轮只做了「**通知**」，完全没做「**列表更新**」。
订单列表是**服务端渲染**出来的一份 HTML —— 长轮询发现新订单后只会弹通知，
DOM 里那一行**永远不会自己长出来**。这是设计缺口，不是 bug。

**改法**：拿到变化后主动同步列表。难点在于「直接 reload 会打断用户」。

| 场景 | 行为 |
|---|---|
| 页面可见、没在操作 | 显示顶部提示条 → **1.8 秒后自动刷新**（并恢复滚动位置） |
| 正在看订单详情 / 勾了订单 / 输入框里 | **只显示提示条**，等操作完或切回页面再刷 |
| 浏览器最小化 / 切走 | 只显示提示条；**切回来的瞬间**才刷新 |

**为什么延迟 1.8 秒**：横幅和系统通知是 `setTimeout(i * 450)` 逐条弹的，
立刻 reload 会让用户**什么都还没看到页面就重载了**。

**为什么不能无脑 reload**：

1. 详情弹窗开着时 reload → 客户信息看不到了；
2. 勾了订单准备批量操作时 reload → 勾选全丢；
3. 输入框里打字时 reload → 输入内容丢。

所以先做 `__shopBusy()` 判断（`.shop-modal` / 勾选框 / `activeElement` 是表单元素）。
刷新前把 `window.scrollY` 写进 `sessionStorage`，加载后 `scrollTo` 还原，避免「一刷新跳回顶部」。

另外用 `__syncTimer` 防止多条订单同时到达时**排队刷多次**。

**提示条**：`#shopSyncBar`，放在订单工具条下方、`if (!$dbReady)` 分支**之前** ——
这样**零订单时也存在**（否则又是一个「没数据显示不出来」的坑）。左边是脉冲小圆点，右边「立即刷新」按钮。

**实测**：调用 `shopSyncList(2)` → 提示条显示且计数为 2 ✓ 未立即 reload ✓ 1.8 秒后 reload=1 ✓
且 `sessionStorage` 里存下了 `scrollY=123` ✓

### 18.9 第五轮修正：付款要时间，超时不能把真客户挡在门外（2026-10-02）

**用户反馈**：「立刻点『我已付款』会推送；过几分钟再点就没推送了。付款是要操作时间的，
哪有这么快完成，起码几分钟。」

**根因**：`api.php` 的 `mark_paid` 只接受两种状态：

```php
if (!in_array($order['status'], ['pending_payment', 'payment_failed'], true)) {
    shop_api_err('该订单当前状态为「…」，无需重复提交');
}
```

而订单会被**自动失效**（`shop_order_expire_unpaid()`，后台每次开页面、前台每次调接口都会跑）：

```sql
UPDATE orders SET status='expired' WHERE status IN ('pending_payment','payment_failed')
  AND created_at < 现在 - N 分钟 AND pay_marked_at = ''
```

N 默认 **10 分钟**。真实付款流程是「扫码 → 切到微信/支付宝 → 输金额 → 确认 → 切回来点按钮」，
实际要 **2~5 分钟**甚至更久。客户超时后回来点「我已付款」→ 订单已是 `expired` →
**接口直接拒绝** → 状态没变 → **不推送、不通知、列表也不刷新**。

**这是一条产品缺陷，不只是通知问题**：客户真的付了钱，却什么也提交不了，
管理员还收不到任何提醒 —— 钱可能就白收了。

**改法**：

1. **允许「复活」**：`mark_paid` 遇到 `expired` 订单时不再拒绝，而是把它改回 `awaiting_verify`，
   让管理员照常核对到账。安全上不吃亏 —— 管理员本来就要人工核对账单，没付钱的单核实后取消即可。
2. **返回 `revived: true`** 和更清楚的提示：「订单曾因超时被标记失效，已把你的付款信息重新提交给管理员核实」。
3. **默认时限 10 → 30 分钟**（只影响新装；已部署站点的 `shop.json` 已存了值，需要手动改）。
4. **后台加动态警告**：失效时间设成 1~14 分钟时，收款页顶部弹红框提示「太短了」并说明原因。
5. **后台说明文案改写**：原文还写着「会被**自动删除**」，其实早就改成软删除了；
   并补上「超时后回来点仍有效」「别设太短」的说明。

**复活的订单不会再被清掉**：`shop_order_set_status('awaiting_verify')` 会写入 `pay_marked_at`，
而失效 SQL 有 `AND pay_marked_at = ''` 双保险。

**实测**：下单 → 改 `created_at` 到 30 分钟前 → 跑失效（变 `expired`）→ 调 `mark_paid` →
接口成功、`revived=true`、状态变「待人工核查」、`pay_marked_at` 记录、`updated_at` 更新；
`shop_order_watch` 返回 `awaiting_verify` 事件（桌面通知会弹）；再跑一次失效**不会**把它清掉。
